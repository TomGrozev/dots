Review gates

to-tickets owns the gate table format and the valid reasons; read them in .omp/skills/to-tickets/REVIEW-GATES.md. Review gate is before build or after build, and a ticket may have both. What you review names the real thing; Reason names a reason by its name. In implement, a before build gate runs the Shape review step and an after build gate runs the See it run step.

## Review gates

| Review gate | What you review | Reason |
|---|---|---|
| before build | How a saved chat keeps its model when the suite changes | Migration: the pin is stored per chat and hard to change later |
| after build | The model picker in the chat header | Taste: tests cannot judge how the picker feels |

The six reason names

Before build: Migration, An outside contract, New structure, Open design. After build: Taste that tests cannot judge. Either kind: The user asked.

Not a reason

The "Not reasons" list lives in .omp/skills/to-tickets/REVIEW-GATES.md with the six gate reasons.

The quiz

  • A numbered list: title, blocked by, what it delivers, mode, review gates.
  • A large breakdown gets a ticket graph: a mermaid in chat, or a page at 6 or more tickets. Either marks the tickets, their blockers and the review gates.
  • The gated tickets in one table: ticket, review gate, what you review, reason.
  • A choice I can only judge with the skeleton in view goes into that ticket's shape review as a decision.
  • I change a mode by editing the ticket's **Mode:** line. It iterates until I approve.

The two review gates

Before build: Shape review

  • The skeleton goes on the ticket's r3 diff artifact: real code, bodies not implemented. Each round publishes the current diff to it, and the first round creates it, whichever gate that is. The placement map shows where the ticket's code goes: each module, file or store it adds, changes, reuses or removes, and who calls or writes whom. 9 boxes at most, each NEW, CHANGED, REUSED, REMOVED or STORED, with a "Why new" line on each NEW box. It goes on a page when the Pages rule calls for one; otherwise it is one mermaid in chat when it has 3 or more boxes.
  • The summary carries the ticket and its gate with the reason, one sentence on what the ticket makes true, 2 to 3 given / when / then examples, the map as a list of boxes, and the page link when there is a page.
  • The two review points that matter most are threads on the lines they concern, each with its evidence, then 0 to 5 decisions. Decisions stay on the diff, even when the page shows the options side by side.
  • A decision: one question, 2 or 3 options (A, B, C), one reason each.
  • The agent's pick stays hidden until I reply. A bare "yes" with open decisions is not an answer.
  • The round ends when I archive the diff and every decision thread has my reply naming an option. The r3-review skill runs the round: each artifact gets its own watch, an async bash job. A watch dies when the session restarts, so the agent runs r3 comment fetch when it resumes. Other tickets keep building.
  • An answer that fixes a hard-to-undo choice becomes an ADR. Later tickets that build on it get edited to match.

After build: See it run

  • The running result, not a plan: a screenshot or a short recording attached to a thread on the same diff, or real command output as text.
  • A change with nothing to see (an API, a migration, a library) shows a real command or test run that exercises it.
  • One line on what to react to.
  • The agent fixes real objections and shows again, before land.

Take the pen, any mode: a build worker fails twice on the same problem with no new hypothesis. I get the repro and the ruled-out hypotheses. I take the pen or give a steer.

<one sentence: what changed and why; skip for a typo, config value or rename>
<only when checks fail: ✗ <command>: <what failed>>

<screenshot link for a UI change; else a part | change table, 5 rows at most; or nothing>

Look at:
- `path:line`: what to check there and why it matters, e.g. what breaks if it is wrong (3 at most; drop the section when none)

Notes:
- a risk to know before merge, or another way to do it, when it has no code line; one line each, 2 at most

On hitl the default is the landing review on the ticket's artifact, then my tidy, then a commit as me. On a PR, my PR review is the hitl review, and the PR waits for it before it merges. commit is not offered for behavioural or multi-file afk work, because it skips the review; when that change has a note and spans several files, recommend PR.

Diagrams and pages

  • A mermaid diagram only for a flow or a structure of 3 or more parts that prose cannot carry. Never for a UI (a screenshot instead), and never to recap the turn.
  • The review happens on an r3 diff: one diff artifact per ticket (per ad-hoc task), and each round publishes the current diff to it. The first round of the ticket creates it, whichever gate that is. Every decision is answered in its threads.
  • A page is a one-screen HTML artifact on r3. It shows what chat text and a diff cannot: how the parts fit together, UI states, or 2 to 3 designs side by side. One is made for a UI change; a new module, API, data shape or migration; a change of more than about 10 files or 400 lines; a choice between designs; a ticket graph of 6 or more tickets; or when I ask. A task worker builds it: screenshots for UI states, else one diagram of at most 9 boxes.
  • In a review, the page is linked from the diff summary, and decisions stay on the diff. On a PR, the body links it. Smaller ticket graphs are a mermaid in chat or in the PR body.

Ask vs do

The ask-first list lives in AGENTS.md § Ask before you act. Local commits and local merges between branches or worktrees are not publishing. Review gates come on top: each row of a hitl ticket's Review gates table, and my review before a hitl change merges. Everything else: it decides, states the assumption, and records a note.
