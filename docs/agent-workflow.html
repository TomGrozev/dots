Review gates

to-tickets owns the gate table format and the valid reasons; read them in .omp/skills/to-tickets/REVIEW-GATES.md. Review gate is before build or after build, and a ticket may have both. What you review names the real thing; Reason names a reason by its name. In implement, a before build gate runs the Shape review step and an after build gate runs the See it run step.

## Review gates

| Review gate | What you review | Reason |
|---|---|---|
| before build | How a saved chat keeps its model when the suite changes | Migration: the pin is stored per chat and hard to change later |
| after build | The model picker in the chat header | Names the user sees |

The six reason names

Before build: Migration, An outside contract, New structure, Open design. After build: Taste that tests cannot judge. Either kind: The user asked.

Not a reason

The "Not reasons" list lives in .omp/skills/to-tickets/REVIEW-GATES.md with the six gate reasons.

The quiz

  • A numbered list: title, blocked by, what it delivers, mode, review gates.
  • A page shows the tickets as a graph, with blockers and review gates marked.
  • The gated tickets in one table: ticket, review gate, what you review, reason.
  • A choice I can only judge with the skeleton in view goes into that ticket's shape review as a decision.
  • I change a mode by editing the ticket's **Mode:** line. It iterates until I approve.

The two review gates

Before build: Shape review

  • The skeleton is written: real code, bodies not implemented. Then I see the intent, 2 to 3 examples, the placement map (NEW, CHANGED, REUSED, REMOVED, STORED, with a "Why new" line; more than 9 boxes get grouped), two review points, and a few decisions.
  • A decision: one question, 2 or 3 options (A, B, C), one reason each.
  • The agent's pick stays hidden until I reply. A bare "yes" with open decisions is not an answer.
  • The build waits until I approve or change the shape and choose in each decision. The build then fills each body test-first.
  • An answer that fixes a hard-to-undo choice becomes an ADR. Later tickets that build on it get edited to match.

After build: See it run

  • The running result, not a plan: a screenshot, a short recording, or real command output.
  • One line on what to react to.
  • The agent fixes real objections and shows again, before land.

Take the pen, any mode: a build worker fails twice on the same problem with no new hypothesis. I get the repro and the ruled-out hypotheses. I take the pen or give a steer.

On hitl, a direct commit needs my r3 review first. On a PR, my PR review is the hitl review, and the PR waits for it before it merges. commit is not offered for behavioural or multi-file afk work, because it skips the review. If both a note and a multi-file change apply, recommend PR.

Diagrams and pages

  • Console: a mermaid block, about 10 boxes at most, short labels.
  • An HTML page on r3 only when I must see the change to judge it:
    • a UI change, with its states;
    • a change that crosses a boundary: a new module or service, or a new data or API shape;
    • one idea larger than about 400 changed lines or 10 files.
  • A task worker draws it: one diagram, about 9 boxes at most, readable without the text.

Ask vs do

The ask-first list lives in AGENTS.md § Ask before you act. Review gates come on top: each row of a hitl ticket's Review gates table, and my review before a hitl change merges. Everything else: it decides, states the assumption, and records a note.
