The table decides the mode. The label says who acts next: a stuck unattended run relabels its ticket ready-for-human, and the mode does not change. Ad-hoc work with no ticket counts as hitl.

Review gates

to-tickets owns this table. No other form. When is before build or after build, and a ticket may have both. What names the real thing; Why names the specific risk. In implement, a before build gate runs the Shape review step and an after build gate runs the See it run step.

## Review gates

| When | What | Why |
|---|---|---|
| before build | How a saved chat keeps its model when the suite changes | A migration: existing chats must migrate to the new pin field |
| after build | The model picker in the chat header | Names the user sees |

A valid Why names one of these

  • Before build: a migration, a change to data that already exists (a schema change, or a format that existing records must migrate). New tables or fields that need no migration are not a reason.
  • Before build: an outside contract (public API, CLI flags or output, a published export, an event payload).
  • Before build: new structure (a new module, or the first instance of a shape that later tickets copy).
  • After build: taste that tests cannot judge (UI, feel, output, names the user sees).
  • Either kind: I asked for it.

Not a reason

  • "It creates new files" or "is this the right place", alone.
  • Size, complexity, tests, bug fixes.
  • Signature changes inside an existing module.
  • Unsure? The agent recommends afk and says so.
  • Deploys, migrations on real data, sent messages: no review gate. The ask-first rule covers them on every ticket.

The quiz

  • A numbered list: title, blocked by, what it delivers, mode, review gates.
  • The hitl tickets in one table: ticket, when, what, why.
  • A choice I can only judge with the skeleton in view goes into that ticket's shape review as a decision.
  • I override any mode by editing the ticket's Review gates table. It iterates until I approve.

The two review gates

Before build: Shape review

  • The skeleton is written: real code, bodies not implemented. Then I see the intent, 2 to 3 examples, the placement map (NEW, CHANGED, REUSED, REMOVED, STORED, with a "Why new" line; more than 9 boxes get grouped), two review points, and a few decisions.
  • A decision: one question, 2 or 3 options (A, B, C), one reason each.
  • The agent's pick stays hidden until I reply. A bare "yes" with open decisions is not an answer.
  • The build waits until I approve or change the shape and choose in each decision. The build then fills each body test-first.
  • An answer that fixes a hard-to-undo choice becomes an ADR. Later tickets that build on it get edited to match.

After build: See it run

  • The running result, not a plan: a screenshot, a short recording, or real command output.
  • One line on what to react to.
  • The agent fixes real objections and shows again, before land.

Take the pen, any mode: a build worker fails twice on the same problem with no new hypothesis. I get the repro and the ruled-out hypotheses. I take the pen or give a steer.

On hitl, a direct commit needs my r3 review first. On a PR, my PR review is the hitl review, and the PR waits for it before it merges.

Diagrams and pages

  • Console: a mermaid block, about 10 boxes at most, short labels.
  • An HTML page on r3 only when I must see the change to judge it:
    • a UI change, with its states;
    • a change that crosses a boundary: a new module or service, or a new data or API shape;
    • one idea larger than about 400 changed lines or 10 files.
  • The designer worker draws it: one diagram, about 9 boxes at most, readable without the text.

Ask vs do

The agent asks me first for:

  1. publishing: commit, push, tag, PR, merge;
  2. deleting or overwriting work it did not create, or rewriting git history;
  3. changing persisted data, a public contract, or an external system (deploys, messages, paid services);
  4. anything with secrets or credentials.

Review gates come on top: each row of a hitl ticket's Review gates table, and my review before a hitl change merges. Everything else: it decides, states the assumption, and records a note.
