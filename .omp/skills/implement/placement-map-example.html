Per-conversation provider pin and model-aware routing

Trigger: structure

Human:structure: Is ShhAi.TargetProvider the right home for the selection rule, and should it be a new module?

Trigger: surface

Human:surface: Does the pin belong on the stored conversation record, in both backends?

Intent

Every turn of a conversation reaches the same provider instance that serves the requested model, so provider-side caching and multi-turn tool sessions stay stable.

Placement map

Why new (TargetProvider): Config.select_provider/0 only drew a random index at request entry. It did not extend, and no existing module owned per-request selection, so the rule had no home.

Acceptance examples

  1. Given a conversation already served by openai_1, when the next turn arrives, then it reaches openai_1 even if another instance also serves the model.
  2. Given two instances where only anthropic_1 lists claude-sonnet-4, when a request names that model, then it reaches anthropic_1 and the conversation pins to it.
  3. Given a request for a model no configured instance serves, when it arrives, then ShhAi answers 404 model "X" not served by any configured provider instance.

Decisions

Decision 1 · Pin location · 3 options

Where does the pin live?

  • AA field on the stored conversation record, written by both backends, kept through the TTL touch.Pick when turns must reach the same instance across restarts and backends: the pin survives eviction-free time and needs no recompute; the cost is an 8th tuple element and a schema write in both stores.
  • BNo stored field. Recompute the target from the model on every turn.Pick when a wrong pin is worse than no pin and the pool is small: nothing to store or migrate; the cost is that provider-side caching breaks whenever the random draw changes instance between turns.
  • CA client-supplied session header that the proxy echoes back to the same instance.Pick when clients already send a session id and own affinity: the proxy stays stateless; the cost is that no header means no pin, and header handling becomes part of the outside contract.

Pick hidden until you answer (structure).

Decision 2 · Pin gone · 3 options

The pinned instance is removed from config. What happens on the next turn?

  • ARe-pin to a configured instance that serves the model, and write the new name back.Pick when the operator's config is the truth and a stale name is a bug: one boolean check, no cache to thrash; the cost is that in-flight conversations move to a cold instance once.
  • BReject the turn with 409 pinned instance is gone and keep the pin.Pick when the client must learn about config drift and re-decide: no silent movement; the cost is that a routine config edit breaks every live conversation until the client reacts.
  • CKeep the pin and serve from any configured instance, so the pin becomes a label only.Pick when availability beats affinity: turns never fail on a rename; the cost is that the cache and session stability the pin exists for are lost the moment it stops resolving.

Pick hidden until you answer (structure).

Decision 3 · Retry pin · 3 options

The pinned instance is unreachable but still configured. A retry succeeds elsewhere. Does the pin move?

  • ANo. The retry is per request. The pin returns to the original instance when it recovers.Pick when provider-side cache is the main gain: an unreachable instance costs no tokens, so keeping the pin is cheap and caching resumes on recovery; the cost is that a long outage keeps drawing fallback targets.
  • BYes. The instance that answered becomes the pin.Pick when a flapping instance should stop being chosen: the pool self-heals toward healthy instances; the cost is that one transient blip permanently moves every conversation it touched off the warm cache.
  • CClear the pin, so the next turn selects again.Pick when model-aware selection should re-judge after any failure: no staleness of any kind; the cost is a full reselect per failure and a cache miss on the next turn.
